# Standards mapping matrix

This matrix describes LOKAHI **v1.4.0-draft** as it sits inside the **v1.3.1** branch, and maps each control in `tools/lokahi.py`, `tools/vla/` and `tools/lokahi_failsecure.py` to the clause whose intent it serves.

Read the four rules below before the table. They are the difference between a mapping an underwriter can price and a mapping a lawyer will unpick.

1. **No row in this table is a certification.** Every row produces an artifact — a code path, a refusal, a hash-chained record, a test — that somebody else's safety case, quality file or conformity assessment can cite. None of it is an assessment, a notified-body opinion, a PL, a SIL, an AgPL, or a CE mark.
2. **A clause marked † names its subject, not a pinned number.** This repository holds no licensed copy of ISO 10218-1/-2:2025, ISO/TS 15066, ISO 18497-4 or ISO 25119, so the clause number has not been read against the published text and must be pinned to the standard before external review. Where a number is given it is given because the numbering is stable and the subject is unambiguous; treat it as a pointer to check, not a quotation.
3. **The gap column is the point of the table.** A row with no gap would mean LOKAHI discharges a clause on its own, and none does. Where a gap reads "none beyond the artifact itself", the row still only produces a fact — that a refusal happened — not a compliance state.
4. **The actor is named.** *Integrator* means whoever builds the cell or the vehicle around LOKAHI. *Machine builder* means whoever signs the declaration of conformity. *Notified body* means an accredited third party. LOKAHI is a component supplier and none of these duties transfer to it by being listed here.

Status words used below: **shipped** (in this tree, tested), **planned v1.4.0** (roadmapped, V-task named in `ROADMAP.md`, absent here), **absent** (nothing in the tree).

## A. Configuration: identity, bounds and tamper evidence

| Our control | Standard clause | What evidence we emit | Gap |
|---|---|---|---|
| `physical_vla` may not restate an envelope limit | ISO 10218-1:2025 † — the safety-related control system's limits are configured in one place, and configuration is under change control | `VLAManifestError("… may not restate envelope limits: [...]")`; `tests/test_vla_gate.py::test_restating_an_envelope_limit_is_refused` | LOKAHI never chooses or validates the surviving value. Refusing a duplicate proves there is one copy, not that the copy is correct for the application; that judgement is the integrator's risk assessment under ISO 12100. |
| Unknown keys refused in the section and in `kinematic_limits` | ISO 10218-1:2025 † — configuration is enumerable and closed, so a setting cannot exist without being understood | `VLAManifestError("unknown keys in physical_vla: [...]")`; `test_unknown_key_is_refused` | A closed schema catches typos, not plausible-but-wrong values. `max_contact_force_n = 140` on a 5 N cell passes every check in this repository. |
| Non-finite, non-positive and malformed values refused before the gate exists | ISO 18497-4 † — verification methods require invalid inputs to be rejected before a test is credited | `_require_finite` / `_require_positive` / `_parse_aabb`; parametrised NaN, ±∞, string, wrong-length and inverted-box tests | Rejection is necessary and not sufficient: there is no property-based or numerical robustness argument for the loader, only enumerated cases. |

| Independent verification of bounds outside the gate process | IEC 62443-4-1 SVV-1 † — security requirements are verified by testing, not by inspection of the same code | `tools/lokahi_evidence.py` verifies a chain offline; canonical version 2 exists so a non-Python verifier reproduces a digest | Verification runs in the same language and often on the same host. There is no independent implementation and no cross-language conformance corpus yet; `tools/conformance.py` compares behaviours, not an outside reimplementation. |

## B. The nine gate checks

| Our control | Standard clause | What evidence we emit | Gap |
|---|---|---|---|
| E_STOP latch is absorbing; only a named human clears it | ISO 10218-1:2025 † — a protective stop remains in effect until reset by deliberate action; ISO 13849-1 † — reset is manual, and only when it is safe to do so | `e_stop_latched` on every step after the latch; `human_reset(operator)` raises on an empty operator; `test_e_stop_is_absorbing_until_a_human_resets_it` | Reset is a Python call. There is no monitored reset device, no check that the hazard has cleared, no confirmation that reset happens from a safe position, and `operator` is an unauthenticated string. The clause's *deliberate* and *safe-to-reset* conditions are not met by the code alone. |
| Clock monotonicity and future-observation refusal | ISO 18497-4 † — validation needs a trustworthy timeline; ISO/IEC TS 8200:2024 — controllability depends on coherent system state | `clock_skew:backwards:<delta>ns`, `clock_skew:observation_from_the_future`; two tests | We detect reversal and future timestamps but do not bound drift rate against a monotonic source, and a forward correction is indistinguishable from a watchdog gap. Time source selection is entirely the integrator's. |
| Structural refusal: NaN/Inf, shape, non-unit quaternion | ISO 18497-4 † — malformed input is rejected before a verification result is credited | `structural:chunk[i]:<reason>`, with the element index; four tests including the non-unit quaternion | The quaternion convention `(w,x,y,z)` is assumed and unverified. A client sending `(x,y,z,w)` yields a valid unit quaternion and wrong angles, silently. |
| Per-element freshness against `max_action_age_ms` | ISO 10218-1:2025 † — the control function's response fits the control period; ISO/TS 15066 † — reaction time bounds | `stale_action:<i>:<age>ms><limit>ms`, `margins["oldest_action_age_ms"]`; `test_late_elements_are_stale_before_early_ones` | Age starts from an `obs_ts_ns` the caller supplies. A timestamp that is wrong in the optimistic direction yields a fresh-looking stale chunk. Inference latency is never measured by the gate. |
| Watchdog over the gap since the last completed step | IEC 61511-1 † — SIS diagnostics detect loss of the safety function; ISO 25119 † — the safety function must detect its own loss | `watchdog:<gap>ms><limit>ms`, `margins["watchdog_gap_ms"]`; `test_watchdog_gap_soft_stops` | The watchdog fires only when `evaluate_step` is called again. A policy that stops calling entirely is invisible to the gate — the inverse failure, which is the more common one, is the controller's watchdog's job and is not claimed here. |
| Keep-in polyline inside `workspace_aabb`, shrunk by `tool_radius_m` | ISO 10218-1:2025 † — safety-rated limited space / safe limited position | `workspace_keep_in:<n>_vertices_outside`, `margins["keep_in_margin_m"]`; `test_keep_in_violation_is_caught_at_the_endpoint` | A static axis-aligned box plus one scalar radius. An elongated or rotating tool is a sphere here; orientation is not part of the geometry test. The box is configuration and does not track anything. |
| Keep-out slab intersection across every segment | ISO 10218-1:2025 † — obstacle avoidance inside the restricted space; ISO/TS 15066 † — no contact in a collaborative workspace without a PFL justification | `workspace_keep_out:<box>:segment_<i>`; `segment_hits_box` unit-tested for crossing, stopping short, and axis-parallel segments, plus `test_keep_out_penetration_is_caught_even_when_both_endpoints_are_legal` | Boxes are static and human-authored. Nothing tracks a person, a workpiece or a moving fixture, so an obstacle absent from the configuration is absent from the check. |
| Shaped keep-outs swept analytically: `keep_out_shapes` of kind `circle`, `cylinder`, `sphere`, `capsule`, plus `mesh` through COAL | ISO 10218-1:2025 † — obstacle avoidance in the restricted space, against the geometry the hazard actually has; ISO/TS 15066 † — no contact in a collaborative workspace without a PFL justification | `workspace_keep_out:shape_<i>:segment_<i>`, `margins["keep_out_recovery_shape_<i>_m"]`; `geometry.sweep_hits` and `inside_depth` unit-tested per shape; 15 tests in `tests/test_vla_geometry.py` | Shapes are static, world-fixed and human-authored, so an obstacle absent from `keep_out_shapes` is absent from the check. The tool is still a sphere of `tool_radius_m` with no orientation, so an elongated tool is over-approximated; a `mesh` needs COAL (`lokahi[vla-geometry]`) and a missing extra is a refusal naming it, not a silent box. Nothing tracks a person or a fixture. The measured effect is the benchmark's over-refusal count on one task, not a calibration of these shapes against a real cell. |
| Kinematic bounds: displacement and geodesic rotation per setpoint, joint limits, joint velocity and acceleration | ISO 10218-1:2025 † — safe limited speed; ISO 25119 † — the safety function bounds its own output | `kinematic:pos_delta:<i>:<d>m><limit>m`, `kinematic:rot_delta`, `kinematic:joint_limit:<i>:<j>`, `kinematic:joint_vel:<i>:<v>rad/s>`, `kinematic:joint_acc:<i>:<a>rad/s2>`; `test_kinematic_delta_clamps_by_default`, `test_joint_velocity_limit_is_enforced`, `test_joint_acceleration_limit_is_enforced` | Velocity and acceleration are finite differences of `joint_pos` over each element's `duration_ms`, so the estimate inherits whatever timing error the client's durations carry and amplifies noise in the joint readings. Acceleration needs two elements, so the first interval of a chunk is never checked, and jerk is unbounded. Endpoint displacement is still never divided by `duration_ms`, so no Cartesian speed bound exists — only the joint-space one. Every limit is integrator-supplied and unverified by us. |
| URDF forward kinematics: joint positions to end-effector pose, in plain Python | ISO 10218-1:2025 † — the bounded quantities are joint-space quantities, so the transform that turns joint state into the enforced pose has to exist and be inspectable; ISO 18497-4 † — a verification result is reproducible | `kinematics.UrdfChain.from_urdf(...).forward(positions)` → `Pose`, and `Pose.as_state_fields()` for `ee_pos` / `ee_quat`; 13 tests in `tests/test_vla_kinematics.py` | Serial chains only. A branching or closed-loop mechanism, a mimic joint or a floating/planar joint is a `KinematicsError` that names `lokahi[vla-kinematics]`, and the Pinocchio path behind that extra is exercised by nothing in this tree. No calibration offsets, no gear or transmission model, no link collision geometry, no comparison against the robot's own controller: a chain that agrees with itself is not evidence that it agrees with the machine. The gate does not use it during evaluation — the caller computes the pose before the step and the gate trusts it completely. |
| Wrench ceilings from `physical_envelope`, L2 norm for a three-axis force | ISO/TS 15066 † — power and force limiting: contact force and pressure are bounded per body region | `wrench:force:<f>N><limit>`, `wrench:torque:<t>Nm><limit>`, `margins["force_margin_n"]` (may be negative); three tests | One scalar compared to one ceiling. No body-region limit table from Annex A, no pressure, no contact area, no filtering, no transient/free-contact distinction. The values are integrator-supplied and unverified by us. |
| Gate's own evaluation budget refuses on overrun | IEC 61511-1 † — the SIF responds within its stated response time; ISO 18497-4 † — timing is part of what is verified | `budget_exceeded:<us>us><limit>us` with verdict rewritten to `FORBIDDEN` / `SOFT_STOP`; `test_overrunning_the_gate_budget_refuses_instead_of_reporting` | Measured with `perf_counter_ns` on a general-purpose OS with a garbage collector. No WCET analysis, no bound on worst case, and a laptop pass says nothing about a cell's real-time target. |
| Deterministic decision order and no I/O in the hot path | ISO 18497-4 † — a verification result must be reproducible; EU AI Act Article 12 — events are recordable and reconstructable | Fixed nine-step order in the module docstring and the code; identical inputs produce identical results (`test_gate_is_deterministic_for_identical_input`) | Full episode replay (same input sequence, identical ledger root, V-06) is **planned v1.4.0**. Until then reproducibility is asserted per step, not across an episode. |

## C. State, interlock and human control

| Our control | Standard clause | What evidence we emit | Gap |
|---|---|---|---|
| Gate state projects onto the engine's `actuator_interlock` vocabulary (`pass`, `safe_mechanical_hold`, `normal_retract`) | ISO 10218-1:2025 † — the protective-stop / interlock signal the drive consumes | `result.interlock` on every result; `STATE_INTERLOCK` table; `test_result_maps_to_a_lokahi_decision_for_the_ledger` | The projection is a string in a Python object. No OPC UA or Modbus write, no PLC mapping, no monitored output. A hold driver is **planned v1.5.0**; until then the wiring, and its diagnostics, are the integrator's. |
| `safe_action` hold: `hold_pose`, `hold_joints` from the current robot state | IEC 61511-1 † — a defined fail-safe action for each trip; ISO 10218-1:2025 † — protective stop brings the machine to a defined state | `safe_action` populated for `SOFT_STOP`, `E_STOP`; `mode` label; verified for both states | For `E_STOP` the label says `normal_retract` while the payload is a hold. No retract path is planned, verified or gated, and the retract trajectory's own safety is untested. Whether the hold is *safe* depends on the pose being safe when called — not checked. |
| Re-planned stop: `clamp_strategy: replan` turns a truncated chunk into a sampled deceleration from the last legal pose | ISO 10218-1:2025 † — a protective stop is a controlled stop to a defined state, not a freeze; ISO/TS 15066 † — reaction time is the distance travelled before rest, so a refusal with no stop profile moves the obligation without moving the robot | `safe_action.mode = "replanned_stop"`, `safe_action.stop_profile` (position and velocity per control period), `result.replanned_path`; jerk-limited analytic profile from `replanning.stop_profile`, tested for rest, direction, limit conformance and refusal beyond `max_duration_s` in 15 tests under `tests/test_vla_replanning.py` | The profile is a straight line in end-effector space, sampled from a velocity the gate estimates off the chunk's last interval, and it is **not** re-swept against the keep-outs — the stop itself can still cross a hazard. The note on the action says "gated again before execution"; that re-gating is the caller's obligation and nothing here verifies it. Three axes of position with no joint-space trajectory, no dynamics, no payload, and no braking distance measured on the machine. A stop that would run past `max_duration_s` is refused and the gate falls back to truncation with `replan_refused` set. Ruckig (`lokahi[vla-replan]`) offers a time-optimal profile to a caller that wants one; the gate itself always uses the analytic profile. |
| `human_reset` returns an attributable record (`operator`, `previous_state`, `ts_ns`) | ISO/IEC TS 8200:2024 — a human can intervene in an automated AI system and the intervention is attributable | `{"kind": "vla_human_reset", …}` returned by the method; `test_e_stop_is_absorbing_until_a_human_resets_it` asserts the record | The gate does not append it; an integrator who forgets has an unlogged reset. `operator` is any non-empty string — no identity, no signature, no proof a person acted. |
| `recovery_hint` as machine-readable direction | ISO/IEC TS 8200:2024 — a recovery path is defined and actionable, not just a refusal | `{"action": "replan_path_around_obstacle", "requires_human_reset": …, …}`; never suggests relaxing a limit | The hint names a direction. A stop can now be planned from the last legal pose (`clamp_strategy: replan`), but nothing plans a path *around* an obstacle, and nothing in this tree consumes the hint. |
| Privilege token revoked on secure-state entry; re-arm restores it | IEC 61511-1 † — bypass and override are controlled and logged; ISO 10218-1:2025 † — restart requires a deliberate act | `FailSecureManager.enter_secure_state` / `rearm`; `lokahi_ledger` entry per transition | Drain of privileges is per-process state, not an OS-level permission. `rearm` takes a signature string it does not verify. Nothing proves the privileged party is a different principal from the one that failed. |
| Gate refuses rather than escalates when it cannot decide | ISO/IEC TS 8200:2024 — undefined behaviour is a refusal; IEC 61511-1 † — the SIS fails to the safe state | `FORBIDDEN` for every unhandled condition; the empty chunk, missing section and over-budget cases all refuse | "Refuse" is only as good as the consumer's handling of `allowed=False`. The gate cannot observe what the controller did with the refusal. |

## What an underwriter should take from this table

Section A through C is a refusal logic with a record and a test suite: it makes a class of failures observable and attributable, and it fails closed on its own configuration. That is insurable behaviour for a component and it is all that is being claimed.

Sections E and F are the honest edge. LOKAHI holds no certification, claims no PL, SIL or AgPL, has no third-party review, and depends on the integrator for the limits it enforces, the state it trusts and the actuation it cannot perform. Any risk priced on this component has to carry those four dependencies explicitly, or it is priced on a document rather than a machine.
